# SP3 — Remote IPC capability spike

## Purpose

Confirm that a runtime `remote` capability (design §2.2.6 `agent_bridge`) actually lets a
**remote** service page invoke `report_unread`, that it is scoped by **both** webview label
and origin (not just one of them), and that the `tauri::Webview` command parameter reliably
yields the calling webview's label — before the real unread-reporting path depends on it.

## Question (design §6.3, SP3)

> Does a runtime `remote` capability let a remote page `invoke` `report_unread`, with the
> exact `AppManifest` permission name?

## Confirmed permission identifier (this spike branch's implementation)

Confirmed **from actual build output**, not just from reading source:

1. `src-tauri/build.rs` declares `tauri_build::Attributes::new().app_manifest(tauri_build::AppManifest::new().commands(&["switch_service", "report_unread", "spike_log"]))`.
2. After `cargo build`, `src-tauri/permissions/autogenerated/report_unread.toml` was generated with:
   ```toml
   [[permission]]
   identifier = "allow-report-unread"
   description = "Enables the report_unread command without any pre-configured scope."
   commands.allow = ["report_unread"]
   ```
3. `src-tauri/gen/schemas/acl-manifests.json` lists this same permission under the `__app-acl__`
   key (the constant `tauri_utils::acl::APP_ACL_KEY`), confirming it is referenced as the bare
   identifier `"allow-report-unread"` with **no** crate/plugin prefix — matching design
   §2.2.6's own example exactly:
   ```rust
   CapabilityBuilder::new(format!("svc-{id}"))
       .remote(format!("{origin}/*"))
       .webview(format!("svc-{id}"))
       .permission("allow-report-unread")
   ```
   (In `tauri-utils-2.9.3/src/acl/resolved.rs`, permission resolution does
   `permission_id.get_prefix().unwrap_or(APP_ACL_KEY)` — an identifier with no `:` prefix is
   treated as an app-level permission automatically, which is why the bare string works.)

The naming rule itself (`allow-$command`, command name kebab-cased —
`report.replace('_', '-')`) is implemented in
`tauri_utils::acl::build::autogenerate_command_permissions`
(`~/.cargo/registry/.../tauri-utils-2.9.3/src/acl/build.rs`), called from
`tauri-build-2.6.3/src/acl.rs`'s `app_manifest_permissions`. The same rule also produced
`allow-switch-service` and `allow-spike-log` for this harness's other two commands.

## Implementation summary

- `src-tauri/src/spike/sp3.rs`: `report_unread(webview: tauri::Webview, count: u32) -> String`
  logs the caller's `webview.label()` and `webview.url()` plus `count`, and returns the label.
- In `sp3::setup` (debug builds only — `cfg!(debug_assertions)`; a release build returns an
  error instead of silently skipping the check), one runtime capability is added:
  ```rust
  app.add_capability(
      CapabilityBuilder::new("spike-svc-allowed")
          .remote(format!("{service_origin}/*"))
          .webview("svc-allowed")
          .webview("svc-allowed-other-origin")
          .permission("allow-report-unread"),
  )?;
  ```
- Three service children are created (shell + these, via the same `Window::add_child`
  multiwebview host the other spike modes use):
  - `svc-allowed` — loads `service_origin` — label **and** origin match the capability.
  - `svc-denied` — loads `service_origin` — label does **not** match (never named in any
    capability).
  - `svc-allowed-other-origin` — loads a _different_ origin (`other_origin`) — its label
    **does** match the capability (chained via a second `.webview(...)` call), but the origin
    does not match `.remote()`'s pattern. This isolates whether label alone is sufficient
    (it should not be).
  - `service_origin` / `other_origin` default to `https://mail.google.com` /
    `https://example.com` and are overridable via `ELUMA_SPIKE_SP3_SERVICE_ORIGIN` /
    `ELUMA_SPIKE_SP3_OTHER_ORIGIN` (see `SPIKE.md`) so the owner can point this at whatever
    real webmail origin they are validating against.
- `capabilities/spike-local.json` (static, loaded from `tauri.conf.json`'s default capability
  set) grants `allow-switch-service` / `allow-spike-log` only to the `shell` and `sp4-page`
  webviews — `svc-allowed`, `svc-denied` and `svc-allowed-other-origin` are never listed
  there, so they start with **no** local-command permissions at all beyond whatever the
  runtime capability above adds.

## Procedure

```sh
pnpm install
pnpm build
ELUMA_SPIKE=sp3 pnpm tauri dev
```

Windows PowerShell:

```powershell
pnpm install
pnpm build
$env:ELUMA_SPIKE = "sp3"; pnpm tauri dev
```

This starts a debug build (SP3's windows only exist in debug builds). Rust stdout logs the
capability that was added and the expected outcome for each of the three children. For each
window, open DevTools and run, in the console:

```js
window.__TAURI_INTERNALS__.invoke("report_unread", { count: 3 });
```

Record, for each of the four behaviours tasks.md Task 0.5 asks about:

1. **`svc-allowed` (allowed label, service origin):** does the call succeed? What does it
   resolve to (the returned label)? Does Rust's stdout show `label=svc-allowed
url=<service_origin>... count=3`?
2. **`svc-allowed` navigated to a different origin:** navigate that same window to
   `other_origin` (e.g. via the address-bar-less DevTools "navigate" or by changing
   `window.location`), then repeat the `invoke`. Does it now get rejected?
3. **`svc-denied` (service origin, wrong label):** does the call get rejected?
4. **`svc-allowed-other-origin` (allowed-label pattern, different origin):** does the call get
   rejected, confirming origin is enforced even when the label matches?

Record the exact rejection error text verbatim (do not paraphrase or normalize it) for any
denied case.

## Constraints and notes for the owner

- A matching webview **label** is not itself an origin check — B4 exists specifically to show
  that a label being in `.webview(...)` does not bypass the `.remote()` origin pattern. Do not
  read a passing B1 alone as proof that origin is enforced; B4 is the actual test of that.
- Behaviour may differ between an iframe on an allowed origin embedded in a denied page and a
  top-level navigation on the webview itself; this spike only tests top-level
  navigation/loading, not iframes. If the owner needs the iframe case covered, note that as a
  follow-up here rather than assuming this spike covers it.
- Do not generalize a result from one OS to the other; if only one OS was run, say so
  explicitly in each Actual cell (e.g. "macOS only, not yet run on Windows").
- A **local** (bundled) window such as `shell` still needs its commands granted through the
  default/static capability set (`capabilities/spike-local.json` here); `report_unread`'s
  runtime capability pattern is specific to _remote_ origins and does not, by itself, affect
  what local windows can call.
- If SP3's debug-only windows could not be created at all (e.g. Task 0.3's scaffold was
  unavailable, or `cargo build` failed), record that as a blocker here instead of leaving the
  results table blank: symptom, reproduction steps, and next steps to try.
